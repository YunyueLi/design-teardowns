# LoL Esports 功能与架构

前一份 `设计解构.md` 拆的是视觉系统。这份拆产品本身：有哪些功能、分布在哪、逻辑怎么走、数据从哪来。

抓取时间：2026 年 9 月 10 日，匿名身份，en-US。
标注约定：**实锤** 指路由、请求或 DOM 实测；**推断** 指观察得出。

---

## 一、功能全貌

整站十一类页面，按路由归纳（**实锤**，逐个访问确认）：

| 路由 | 功能 | 状态与特征 |
| --- | --- | --- |
| `/en-US` | **赛程**。直播、今日、未来、历史四类比赛聚合 | 根路径即此页，无独立首页 |
| `/en-US/gpr` | **全球战力排名**。跳转到 `/gpr/2026/current` | 年份分档 2026 / 2025 / 2024，带快照与更新时间戳，表格呈现 |
| `/en-US/pickems` | **赛事竞猜**。按赛事分卡，猜冠军换奖励 | 有 ENDED 等状态标；本次抓到 MSI 2026 与 Worlds 2026 |
| `/rewards` | **观赛奖励**。看直播掉落 | **唯一强制登录的功能**，未登录直接跳 Riot 账号页 |
| `/en-US/news` | **新闻列表**。LOAD MORE 增量加载 | |
| `/news/<slug>` | 新闻正文 | |
| `/en-US/tickets` | **门票**。跳转 `/en-US/tickets` | 不是商城，是「Fan First Access」资格窗口，抓取时状态为 CLOSED |
| `/en-US/results` | **其他联赛**。跳转到具体赛事阶段 | 二级联赛的排名，横向切联赛（Americas Cup、Arabian League、EMEA Masters 等） |
| `/en-US/tournament/<id>` | **赛事页**。跳转到 `/overview` | 赛程、排名、战队；本次抓到 Worlds Standings |
| `/en-US/season/<id>/handbook` | **联赛手册**。赛制规则说明 | |
| `/vod/<matchId>/<gameNumber>` | **录像回放**。按「比赛 + 第几局」定位 | 首页一屏就挂了三十余个此类链接 |

功能可分三层：

- **核心层**：赛程。它是根路径，也是其余功能的入口来源。
- **周边层**：排名、新闻、赛事页、手册、录像、其他联赛。都不需要登录，都从赛程或顶栏进入。
- **账号层**：竞猜与奖励。唯一需要 Riot 账号的两项，也是唯一有「获得物」的两项。

## 二、功能怎么分布在屏幕上

桌面端三栏，每栏承担的职责完全不同（**实锤**）：

```
┌──────────────────────────────────────────────────────────┐
│ Riot 通用顶栏（跨产品共用组件，非本应用所有）              │
│ HOME  EVENTS & STANDINGS▾  POWER RANKINGS  PICK'EMS      │
│ REWARDS  NEWS  TICKETS            语言  LOGIN            │
├───────────┬──────────────────────────────┬───────────────┤
│ 左栏       │ 中栏                          │ 右栏          │
│ 导航入口   │ 产品本体                      │ 他处功能的橱窗 │
│           │                              │               │
│ 赛季时间轴 │ 直播卡                        │ 排名前三      │
│ 七个赛段   │ 今日比赛                      │ 查看完整排名 →│
│ ↓ 各赛区   │ 更早的比赛                    │               │
│ 联赛手册   │ Load More                    │ 新闻三条      │
│ 其他联赛   │                              │               │
│ （不滚动） │ （唯一滚动区）                 │ （独立滚动）   │
└───────────┴──────────────────────────────┴───────────────┘
```

这个分布有明确逻辑：

- **左栏是纵深导航**，把时间轴当成目录。七个赛段按时间纵排，每段展开是各赛区的赛事页入口。用户在这里回答「我要看哪个赛事」。
- **中栏是产品本体**，也是全站唯一的主滚动区。用户在这里回答「现在有什么可看」。
- **右栏是别处功能的橱窗**。排名和新闻在这里各露三条，点进去才是完整页面。它不承担任何自身完整的功能，职责是把流量导向周边层。

移动端（390px）三栏塌成一栏，左右两栏收起（**实锤**）。中栏内容顺序不变，说明**中栏本来就是自足的**，两侧栏是增强而非必需。

## 三、赛程的数据逻辑

首页加载时并发三个 GraphQL 请求，全部走同一个端点 `/api/gql`，操作名 `homeEvents`（**实锤**）：

| 用途 | 时间窗 | 状态筛选 | 类型 | 页大小 |
| --- | --- | --- | --- | --- |
| 今日前后 | 前 2 天 至 当日结束 | `["completed","unstarted"]` | `all` | 300 |
| **直播中** | **不限时间** | `["inProgress"]` | `all` | 300 |
| 未来赛程 | 当日 至 60 天后 | `["unstarted"]` | `match` | 40 |

这三条拆得很有讲究：

1. **直播中的比赛不受时间窗约束。** 单独一条查询，不带任何日期参数。原因很实际：一场比赛可能跨零点，也可能因加赛拖到窗口之外，用日期筛会漏。**状态比时间更可靠**，所以直播单独按状态查。
2. **今日前后用 300 的大页，未来用 40 的小页。** 今日附近要求一次拿全、不能有二次加载的空窗；60 天的未来赛程只需要够填满屏幕。
3. **前两条 `eventType: "all"`，第三条 `"match"`。** 「今日」要显示所有事件类型（含表演赛、开幕式一类），「未来」只列正式比赛。

### 向过去翻页用的是游标，不是日期

点 Load More 触发的是第四种形状（**实锤**）：

```
eventState: ["completed"]   eventType: "match"   pageSize: 40
pageToken: "b2xkZXI6OjExNTU2NDc5NzE2MzgyMTE3NQ=="
```

这个 token 做 base64 解码是：

```
older::115564797163821175
```

即「比这个事件 ID 更早的一批」。**向未来用日期窗，向过去用游标**，两个方向两套策略。这不是不一致，是各自选了对的工具：未来的赛程表是已排定的、稀疏的，按日期切最自然；历史比赛密集且无限延伸，游标翻页才不会因为某几天没有比赛而翻空。

### 联赛筛选在前端做

点开 All Leagues 面板并操作，不产生任何新请求（**实锤**）。既然首屏已经把 300 条拉进内存，筛选就没必要回服务端。代价是筛选结果受限于已加载的范围。

### 日期切换不改 URL

日期控件的三个按钮语义清晰：`PREVIOUS DATE`、`Today`、`NEXT DATE`（**实锤**，取自 `aria-label`）。但切换日期后地址栏仍是 `/en-US`（**实锤**）——**日期是客户端状态，不是路由**。

这意味着用户无法把「9 月 6 日的赛程」发给别人，也无法用浏览器后退回到上一个日期。对一个高频分享赛果的社群产品，这是个明确的取舍，代价不小（**推断**：换来的是切日期零导航开销与滚动位置保持）。

## 四、剧透逻辑贯穿全栈

剧透保护不只是首页的一层遮罩，它是一条贯穿数据与界面的规则（**实锤**）：

- 请求层：`vodType: ["recap"]` 随「今日前后」那条查询一起要回放数据，**结果与回放是一起拉的**。
- 界面层：已结束的比赛用 `#262626` 遮罩盖住比分区，粒度分两级——只遮比分，或整张卡连队名一起遮。
- 状态层：`inProgress` 的比赛不遮。正在打，没有结果可剧透。
- 偏好层：齿轮面板里唯一的开关，匿名默认开启，存 `localStorage` 的 `spoiler-protection` 键。

**由此可以理解整个赛程页的排序为什么是「直播 → 今日 → 更早」而不是按时间倒序。** 直播不需要保护，放最前；今日的已结束比赛需要保护，但用户最可能想看；更早的比赛保护价值递减，往下沉。排序本身就是按「剧透风险 × 关注度」排的。

## 五、跨产品架构

三处证据指向同一个结论：**这不是 LoL 专用的站，是 Riot 电竞站群的一套壳。**

1. **数据层**：`homeEvents` 和 `GetPickemsTournamentsSimple` 都带 `sport` 参数，取值 `lol` 与 `LOL`（**实锤**）。
2. **样式层**：五个 `[data-theme]` 块并列，`lol`、`val`、`wr`、`tft`、`rb`，各自重定义同一组语义色（**实锤**，详见 `设计解构.md`）。
3. **字体层**：预加载 27 支字体，覆盖各品牌展示体与六个文种（**实锤**）。

同一套组件，换 `sport` 参数取数据、换 `data-theme` 取配色、换字族取排版。顶栏更彻底——它是 Riot 跨产品共用的独立组件（DOM 里的 `riotbar-header`，内容清单从 `cdn.rgpub.io` 单独拉取，**实锤**），字体用的是 Colfax 而非站内的 Inter。

**所以这个站的边界要划清楚**：顶栏不属于它，直播播放器不属于它（iframe 嵌第三方平台），登录不属于它（跳 Riot 账号）。它自己负责的，是三栏壳层加赛程逻辑。

## 六、四个值得记的产品判断

1. **根路径给了工具，不是给了品牌。** 没有营销首页，打开就是赛程。Riot 有的是地方讲品牌故事，这里只解决「今天看什么」。
2. **唯一的设置项是剧透开关。** 没有主题、没有时区、没有通知。设置菜单的长度暴露了团队对「用户真正需要控制什么」的判断。
3. **只有能给东西的功能才要登录。** 竞猜和奖励要账号，其余全部匿名可用。查赛程、看排名、读新闻、看回放都不设门槛。
4. **右栏不做完整功能，只做橱窗。** 排名和新闻各露三条就跳走。这让中栏得以保持单一职责，也让周边功能有稳定的曝光位。

## 七、局限

- **登录后的形态未验证。** 竞猜的填写流程、奖励的掉落记录、偏好是否改为账号绑定，均未测。
- **GraphQL 只抓到四个操作**（`homeEvents`、`GetSeasonForNavigation`、`GetPickemsTournamentsSimple`、`GetTeamGpr`）。这是本次访问路径覆盖到的，赛事页、录像页的查询未逐一记录。
- **日期切换的加载行为未测全。** 确认了不改 URL，但点击后是否复用已加载数据、还是在某个跨度后重新取数，没有测到边界。
- **各赛区直播平台的差异未验证。** 抓取时段命中的是一个韩语区平台的嵌入。
